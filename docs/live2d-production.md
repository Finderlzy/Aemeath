### V21-T01 实测记录（2026-09-15）

**抠图与分层已通过，Cubism 三步必须在编辑器内手动完成。**

**透明抠图（通过）。** 原稿为浅灰底（约 `230,227,226`，占 78% 像素）。按颜色阈值直接剔除会连白裙与浅肤一起删掉，因此改为**从图像边缘做洪水填充**：只有与边缘连通的背景色区域才算背景，角色轮廓内部的同色像素保持不透明。实测：透明 78.8%、软边 10.3%、不透明 10.9%；白／黑／彩色三种背景下均无灰底、无棋盘格，且无任何"明显属于角色"的像素被误删（该判据以原图色彩距离 >40 为界，实测 0 个）。半透明边缘做了反混合，避免在深色背景上留灰边。

**最小分层（通过）。** 用 Krita 5.3.3 建立 9 层工程并导出 PSD，全部图层共享 1254×1254 同一画布坐标，参考层锁定、身体参考层隐藏。PSD 用 Krita **读回验证**：8 个图层的名称、顺序、坐标与不透明度全部正确。

**moc3 版本是本次最重要的结论。** 实测两个 Core 的上限：

| Core | 能读的最高 moc3 版本 | 证据 |
| --- | --- | --- |
| Cubism 5.3 Editor 自带 | **6** | `csmGetLatestMocVersion = 6` |
| 现有客户端 WebSDK | **5** | 仅定义到 `MocVersion_50`；自带样例 `mao_pro` 为 ver=5、`shizuku` 为 ver=3 |

**因此 Cubism 5.3 默认导出（ver=6）会被现有客户端拒绝**，报 `csmReviveMocInPlace is failed. The Core unsupport later than moc3 ver:[5]`。导出时必须把 `[Export settings]` 的 **(1) Export version** 选为较旧 SDK 版本，使 moc3 版本号 ≤ 5。这不是可选优化，是能否加载的前提。

**Cubism 自动化边界（实测，非推测）。** 导入 PSD、建立变形器、导出 moc3 三步**必须人工在 GUI 中完成**：编辑器是 Java/Swing 程序，无任何命令行导出入口；其自带 `Live2DCubismCore.jar` 只有运行时类（`CubismMoc`、`CubismModel`、`CubismParameters`），只能读 moc3 不能生成；官方 External API 只能读写参数，且默认关闭、需在 GUI 内手动开启。Krita 侧同样受限：无 GUI 时 `exportImage` 会阻塞在模态对话框（PNG 与 PSD 都如此），`saveAs` 到 `.psd` 同样阻塞，因此分层工程由 Krita 生成、PSD 由脚本写出再用 Krita 读回校验。

用户已安装软件，2026-09-14 已核实 `D:/Program Files/Live2D Cubism 5.3/CubismEditor5.exe`（5.3.00）、同目录 `CubismViewer5.exe` 及 `D:/Program Files/Krita (x64)/bin/krita.exe` 文件存在。这些为本机位置，不是代码硬编码依赖。启动已实测：Cubism 标题栏显示 `[ FREE版 ]`（未注册，**未启动 PRO 试用**），Krita 5.3.3 正常启动。不能通过编写 model3.json 代替实际绑定或生成 moc3。

第一项技术小样使用原稿副本和少量眼／嘴图层，走「保存 → 重开 → PSD 导入 → 一个参数变形 → moc3 导出 → 现有 Core 加载」。分层与 PSD 已完成，并由 Krita 读回验证图层名称、顺序与坐标；Cubism 三步的操作步骤见 `references/character/live2d/CUBISM-MANUAL-STEPS.md`（本地文件，不入版本管理），完成后由 `scripts/probe_live2d_core.js` 验证在现有客户端 Core 中加载并驱动参数。

**FREE 版限额与后续影响。** 已核实 FREE 版每模型最多 1 张纹理（≤2048px）、100 个 ArtMesh、30 个参数、50 个 Deformer。本小样远在限额内，**不需要购买或启动 PRO**；但**完整身体分层在 FREE 限额下会紧张**，T02 需据此评估是否升级或拆分为多模型。

## 分层验收

1. 抠图包含真实 alpha，在白、黑、彩色背景下检查发丝、半透明衣摆与头饰，无灰底残留或棋盘格。
2. 可见层按原位置叠加后与定稿一致；隐藏补画不影响默认外观。
3. 五官可独立隐藏，眼白、脸底和口腔完整；轻微移动部件不产生明显空洞。
4. 所有图层共享同一画布坐标；PSD 保留可编辑层及唯一图层名，导入 Cubism 后核对顺序和透明效果。

## 首轮绑定目标（制作建议，尚未验收）

| 参数 | 用途 | 建议范围 |
| --- | --- | --- |
| ParamAngleX / ParamAngleY / ParamAngleZ | 小幅转头、抬低头、歪头 | 参数 -30～30，画面变形先控制在自然小幅度 |
| ParamEyeLOpen / ParamEyeROpen | 左右眨眼 | 0～1，默认 1 |
| ParamEyeBallX / ParamEyeBallY | 视线移动 | -1～1，默认 0 |
| ParamMouthOpenY | 音频驱动开合嘴 | 0～1，默认 0 |
| ParamMouthForm | 嘴角表情 | -1～1，默认 0 |
| ParamBodyAngleX / ParamBreath | 身体轻摆与呼吸 | 前者 -10～10；后者 0～1 |

首轮制作呼吸、眨眼、口型和轻微头发物理；点头、摇头、开心等在基础闭环后扩展。走路、盖被子与完整生活场景不包含在此轮基础绑定中。

现有客户端 `vendor/Open-LLM-VTuber-Web/src/renderer/WebSDK/src/lappmodel.ts` 已读取模型 EyeBlink／LipSync 参数组，并有 ParamMouthOpenY 回退路径。导出时仍应明确配置 EyeBlink 与 LipSync 分组，不依赖回退。客户端会叠加视线与呼吸参数，绑定完成后须检查与动作是否冲突。

## 运行交付目标

- 保留分层 PSD、Cubism 可编辑工程及源纹理。
- Cubism 导出真正的 `.moc3`、`.model3.json`、纹理，按实际制作内容附带 `.physics3.json`、`.exp3.json`、`.motion3.json`。
- 使用现有客户端验证加载、眨眼、说话口型、停止发言闭嘴、静音状态以及实际桌面尺寸显示。
- 当前不替换上游示例模型、不修改运行配置，不把平面立绘标记为已完成 Live2D。

## 集成契约与验收口径

模型标识计划为 `aemeath`，运行入口为 `/live2d-models/aemeath/runtime/aemeath.model3.json`。如果实际导出目录不同，先同步契约与 model_dict 的相对引用再集成。复用 `character_config.live2d_model_name` 选用模型，复用 `model_dict.json` 的 `url`、`kScale`、`initialXshift`、`initialYshift`、`kXOffset`、`emotionMap`（实际支持项由集成时客户端核对），不新建一份不被渲染器读取的配置。

导出明确设置 EyeBlink 为左右眼开合、LipSync 为 ParamMouthOpenY。口型由实际音频播放驱动；停止、打断、TTS 失败、静音时清零并拒绝迟到音频恢复旧口型。静音不停止呼吸和眨眼。待机／物理不得覆盖嘴部开合；具体叠加顺序由 T03／T04 实测固定。

模型包先在隔离目录检查 model3 的所有相对引用、moc3、纹理、物理／动作文件，再真实加载。可实际使用的包才允许应用；失败保留上一模型和配置。多文件配置写入复用 v2 的保存／生效约定，记录备份与恢复结果，不声称可自动热更新。正式身份按经过验收的资产清单判定，不因目录名或非示例名而认定正式。

T03 先在隔离客户端验证模型基础动态，不依赖桌面窗口完成。T04 在 v2 提供管理选用接口与桌面会话接入后验证管理选用、缩放位置、重启、真实语音与字幕；v2 侧对应 V2-T02 [#15](https://github.com/Finderlzy/Aemeath/issues/15)（已关闭，管理选用接口可用）与 V2-T03 [#16](https://github.com/Finderlzy/Aemeath/issues/16)（open，桌面会话接入待完成），后者满足后集成。T05 从交付包重建并走 Windows 桌面全流程，包含 100%／150% 系统缩放、建议 250／350／500 像素角色高度下的脸部辨识、发丝边缘、任务栏与字幕可读性；具体可用范围与性能读数如实记录，不凭计划宣称达标。

验收至少覆盖待机、说话、打断闭嘴、课堂文字、退出课堂恢复语音、隐藏恢复、重连不重播、模型丢失／损坏回退及重启后选择保持；回归真实对话与本地记忆，不能以模型 Viewer 能打开代替桌面集成。正式角色替换不创建第二个音频队列、会话或回执来源。
