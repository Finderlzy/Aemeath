# Aemeath 需求

更新：2026-09-13。本文整理用户已表达的需求；建议和待定项分别标注。首期已有实现，真实验收部分完成；剩余工作见 [实施计划](implementation-plan.md)。本次新增的情绪互动、音量检查与微信代答属于后续规划，尚未实现或验收。

## 目标与角色

面向用户个人 Windows 电脑的长期 AI 伙伴。以桌面为家，能够观察、聊天、记忆、主动行动和实际操作电脑。QQ、微信只是未来的互动渠道。

独立于“大肥鱼”，不继承其角色、记忆或账号状态。角色原型为《鸣潮》爱弥斯；支持简单默认人设和可选角色预设。具体角色设定、声音与美术资产尚未确定，不编造原作设定。

## 已确认首期

用户已接受：桌面角色、语音与文字聊天、记忆、屏幕感知、主动搭话。

- 用户工作时，她可结合屏幕内容主动语音搭话；用户可点击输入框打字，也可直接说话。
- 用户告知“我在上课”后进入课堂状态，后续使用文字交流；打字本身不等于要求永久静音。
- 可像同事摸鱼一样闲聊、接续旧话题、适时主动发起话题，而非只回答任务。
- 在相处中积累对用户的了解，形成持续关系。

建议首期验收：完成一次屏幕驱动的主动搭话与两种输入方式的接续对话；重启后召回用户明确提供的事实；课堂状态下不播放普通回复和主动搭话语音；用户忙碌或不回应时不连续追问。记忆纠正、删除、语音打断、主动频率参数为建议能力，未单独确认。

## 完整愿景，分期实现

1. 作息：根据时间和上次互动表现睡醒、困倦和埋怨；夜间走到床上盖被子。关机后下次启动推算状态，不需要关机期间运行。具体时间、睡眠时是否接受打扰待定。
2. 课堂监督：区分查资料与走神，保存用户正在做的内容，关闭相应活动，发“认真听课！”及表情包。保存需检查结果；无法确认时如何处理待定。
3. 维护用户：理解 QQ/微信聊天中的诋毁，自主生成并向对方发送角色语音。须区分本地播放与原生语音消息；具体平台能力、联系人范围与误判处理待验证。
4. 提醒吃药：记住用户提供的安排，到时提醒；建议独立记录提醒与服用确认，不从未回复推定已服用。具体时间与内容待配置。
5. 电脑行动：用户希望赋予较大自主权，角色应结合价值判断和上下文决定行动。具体执行范围尚未细化；本条是产品设计目标，不授权开发期间发送真实消息或关闭用户应用。

## 新增场景：情绪互动与消息代答

以下场景及行为边界于 2026-09-13 确认，属于后续范围，不加入首期完成条件。具体实现方案和实施顺序尚未确定；角色表现、状态判断与电脑行动仍由统一协调逻辑处理。

### F01：生气后躲起来

用户在对话中惹她生气时，她可以转身、躲到屏幕边缘、暂时减少回应，表达“不想理你”；用户安抚后逐步恢复交流。情绪是可恢复的角色状态，不能使功能失联：明确求助、停止指令和重要提醒仍须响应。

验收时应观察到躲藏、减少回应和安抚后恢复的过程，并验证躲藏期间仍能处理明确求助与停止指令、正常送达重要提醒。触发尺度、持续时间、自然恢复方式和具体动画待设计。

### F02：没有回应时检查声音并切换交流方式

她说话后没有得到回应时，先结合刚才的对话、用户是否离开、课堂或专注状态判断原因，不直接认定用户故意不理她，也不连续追问。可检查系统与应用静音状态、音频输出设备是否变化，并以“跑到音量图标旁看看”等动作表现检查过程；检测不可用时不声称已经确认原因。

发现声音关闭，或判断当前不适合说话时，改用文字交流，例如“原来你把声音关了呀”。尊重用户关声音的选择，不自行恢复音量；课堂状态持续约束输出，不因输入方式或情绪变化解除静音。

确认适合互动时，可以探头、敲屏幕边缘或发文字气泡吸引注意，并带点情绪问“为什么不理我？”。允许语音且适合播放时可同时使用文字和语音。最小化用户当前窗口仅作为用户主动开启的“允许闹脾气”玩法，限定可操作的应用和场景，执行后核对目标及结果；默认不开启。

验收覆盖静音、课堂、用户离开、正常可交流及音量检测不可用的分支：不得把未回应当成故意忽视，不连续追问，不自行开声音；未开启玩法或窗口不在允许范围内时不最小化。无回应等待时间、专注与离开的判断方式、提醒频率和可操作应用范围待设计。

### F03：微信联系人着急找用户时代答

用户微信挂着，某联系人连续发来消息；她结合消息内容和刚才的聊天，判断对方是否急着找用户。消息数量仅作为线索，不能单凭连续消息决定回复。知道用户去向不等于获准向他人披露，代答须有一次性交代，或针对指定联系人及信息范围的长期授权。

例如，用户出门前说“我去取快递了，如果小王找我，你帮我说一下”。小王随后来找时，她可回复：“我是 Aemeath，他刚才说去取快递了，回来后我会提醒他看消息。”身份声明放在开头，只使用有依据且在授权范围内的信息，不推测去向、返回时间，也不替用户答应事情。没有相应授权时不自动代答。

默认采用文字；预先允许语音代答时，可使用她自己的声音发送，并同样先表明身份。微信原生语音消息与本地语音播放是不同能力，平台发送能力须单独验证。用户回来后，告知谁来找过及实际回复内容；联系人、授权依据、回复内容与发送结果保存在本地。

验收先用隔离会话或替身覆盖：有授权时准确代答并声明身份，无授权、联系人不匹配或信息超出范围时不发送，不编造信息或承诺；核对实际发送结果并验证回报与本地记录。随后再在明确授权的真实会话中分别验收文字和原生语音。授权有效期与撤销方式、重复消息处理、发送失败处理及微信接入方案待设计。本条不授权开发验证期间向真实联系人发送消息。

## 约束与技术偏好

- 对话等模型计划走 API，用户担心本地模型效果。
- 记忆必须本地持久化：聊天历史、用户事实、经历摘要、表达与黑话、角色状态、提醒及检索索引均存放在用户电脑，不使用云端记忆托管、远程向量数据库或自动云同步。
- 已确认本地存储与模型部署分离：提取、总结、嵌入等模型处理可走 API，仅发送本次处理所需内容，结果回写本地。调用 API 会向提供商发送输入，不代表提供商必定零留存；选定服务时核对其数据留存选项。无需为记忆功能强制运行本地模型。
- 借鉴 MaiBot 的人设、记忆、表达与黑话学习，优先评估现有可复用技术。
- 云端屏幕/语音处理的具体范围、API 提供商和月预算未确定。API 模型需要发送对应输入，本地存储不等于输入不会离开电脑。
- 不把大肥鱼的数据库、私聊、凭据或运行配置复制进新项目。

## 当前阶段边界

首期不要求完成通用电脑操作、QQ/微信代发、完整卧室动画，以及 F01–F03 的情绪躲藏、音量检查、窗口最小化玩法和微信代答。这些仍属于后续目标，不删除需求；本次不改变既有首期验收标准。
已确认优先以 Open-LLM-VTuber 验证桌面与语音能力，连接独立角色和本地记忆服务。

首期实现状态见 [验收记录](acceptance.md)：真实文字对话、提取与屏幕视觉已有通过记录；
嵌入检索阻塞，语音、主动交流完整流程和人工试用未完成。局部通过不能替代首期整体验收。

## 需求标识与验收对应

以下 R/E 编号用于追踪原有首期范围；新增后续场景使用上文 F01–F03 编号单独追踪。轮数、延迟和数据集判据沿用
[验收操作指南](acceptance-guide.md) 与 [真实验收记录](acceptance-live.md)，属于现有工程验收口径。

| 标识 | 已有范围与规则 | 可观察的完成标准 |
| --- | --- | --- |
| R01 | Windows 桌面角色，文字与语音聊天 | 实际客户端可启动，文字、麦克风输入均能得到可见／可听回复；浏览器文字通过不等于桌面语音通过 |
| R02 | 课堂状态持续约束输出 | 输入“我在上课”后普通回复及主动搭话仅文字，后续打字不解除静音；重启保持按现有方案验证 |
| R03 | 本地记忆与持续关系 | 事实及来源留在本地；重启后用不同问法召回；同一会话历史回忆不能替代长期检索 |
| R04 | 屏幕感知 | 描述当前前台窗口，切换不串画面；关闭后停止观察且不保留迟到摘要；锁屏及窗口不可用有明确结果 |
| R05 | 结合情境主动搭话 | 不点击观察或发送搭话信号也能结合有效屏幕信息开口；用户打字／说话时不抢话；不回应后不连续追问 |
| R06 | 本地数据边界 | 聊天、记忆和索引本地存储，无远程记忆托管或自动同步；模型调用仅发送所需输入 |
| E01 | 已实现的建议能力：打断、纠正、遗忘与频率配置 | 按既有验收清单验证；保持“建议能力”来源，不因已有代码改成新确认需求 |

术语：**课堂状态**是持续的输出约束；**主动候选**是尚未确认显示的生成内容；
**已送达搭话**以客户端显示回执确认；**屏幕摘要**只有在观察开启、来源窗口及有效期满足约束时才能进入对话。
实现不符时登记缺陷，不修改完成标准迁就实现。

ASR/TTS 使用 API 是现有验收方案的技术目标；本地 SenseVoice 与 edge-tts 通过也不能记为 API 验收通过。
若拟将现有引擎作为首期最终方案，需另行确认范围调整；本轮保留原验收要求。
